## Context

当前全市场行情库 `market_data.db` 的 K 线下载通过 `stock-sdk.getHistoryKline()` 访问东方财富历史行情。全量回填与手动增量已具备任务队列、断点续跑、失败重试、限速、质量检查、复权因子物化和派生周/月线等能力，但这些能力的 K 线来源单一。

搜狐 `hisHq` 可提供 A 股/ETF/北交所的日线历史行情，支持 `period=d/w/m`、`order=A/D` 和一次请求多个 `cn_` 代码。实测确认：搜狐只返回不复权价格，但涨跌额/涨跌幅按除权口径给出，可用于本地推导复权因子；未发现可用的服务端 qfq/hfq 参数。

本 change 只调整行情库全量回填与增量下载的 K 线来源，不改变自选股页面手动下载、每日 15:10 自动下载、图表读取、资金估值和形态识别路径。

## Goals / Non-Goals

**Goals:**

- 将行情库全量回填与增量下载的 K 线请求切换到搜狐 `hisHq`。
- 保持 `MarketSdkLike` 上层契约不变，`getHistoryKline()` 继续返回 `MarketKlineItem[]`。
- 保持 `raw_daily / qfq_daily / hfq_daily` 三类任务、任务键、`last_success_date`、失败重试和质量检查语义不变。
- 在适配器内基于搜狐原始日线与涨跌信息推导 qfq/hfq，使上层同步服务无需感知数据源差异。
- 为行情库数据建立新的来源标识 `sohu_hisHq`，并要求切换后重新全量回填，避免与东财数据混用。

**Non-Goals:**

- 不改变自选股业务库 `stockanalyzer.db` 的下载、读取与展示逻辑。
- 不改变 IPC 接口、前端页面、数据库表结构和迁移文件。
- 不替换证券池、交易日历、名称补全和搜索的数据源；这些能力继续由 `stock-sdk` 提供。
- 不引入新的 npm 依赖。
- 不实现搜狐多数据源交叉校验或自动回退东方财富。
- 不宣称搜狐提供服务端 qfq/hfq。

## Decisions

### D1：改造边界限定为行情库 K 线下载

**决策**：只在 `marketSdkClient.ts` 中替换 `getHistoryKline()` 的实现；`getAShareCodeList / getTradingCalendar / getAllQuotesByCodes / search` 继续委托 `StockSDK`。`marketDataSyncService.ts` 的任务生成、调度、落库和因子刷新逻辑保持不变。

**理由**：用户已明确选择只替换行情库全量回填和增量下载，自选股手动/自动下载维持现状。该边界可以把影响面收敛到一个适配器和少量 wiring。

**备选方案**：建立覆盖所有 K 线下载的全局数据源抽象。  
**未采用原因**：会改动 `klineDownloadService.ts`、UI 与既有自动调度，超出本 change 范围。

### D2：`marketSdkClient.ts` 改为混合客户端

**决策**：`createMarketSdkClient()` 内部同时持有 `StockSDK` 与新的搜狐 K 线客户端：

- 非 K 线方法委托 `StockSDK`
- `getHistoryKline(symbol, { period:'daily', adjust, startDate, endDate })` 委托搜狐适配器

`MarketSdkLike` 接口不变，`marketDataSyncService` 无需感知数据源切换。

**理由**：证券池、交易日历和名称补全已经经过验证，继续保留可以复用已有能力；同时避免改动同步服务的调用签名。

**备选方案**：把 `MarketSdkLike` 拆成元数据接口和 K 线接口。  
**未采用原因**：会引发同步服务、测试和依赖注入的大范围改动，收益不足以抵消本 change 范围扩张。

### D3：搜狐请求与字段归一化

**决策**：

- 代码格式：`sh600519 / sz000001 / bj920819` → `cn_600519 / cn_000001 / cn_920819`
- URL：`https://q.stock.sohu.com/hisHq?code=<cn_code>&start=YYYYMMDD&end=YYYYMMDD&period=d&order=A&stat=0&rt=json`
- 响应通过 `TextDecoder('gbk')` 解码
- `status !== 0` 或空响应视为失败，抛给现有重试机制
- 字段映射：日期、开、收、涨跌额、涨跌幅、最低、最高、成交量、成交额、换手率
- 涨跌幅/换手率去掉 `%`
- 成交额按“万元 → 元”转换，并在实现阶段用东财样本回归确认
- 振幅本地计算：`(high - low) / previousClose * 100`，首日置空
- 返回第 11 个字段时暂不处理，不将其视为复权价
- 返回值再次按日期升序排序并按日期去重

**理由**：搜狐接口只提供原始日线且编码为 GBK；字段映射需要与 `MarketKlineItem` 对齐，确保现有 `toDailyBars()` 与落库逻辑不变。

**备选方案**：让上层服务直接解析搜狐响应。  
**未采用原因**：会把数据源细节泄漏到同步服务，破坏现有接口边界。

### D4：本地复权因子引擎

**决策**：新增独立因子推导模块，基于搜狐原始日线、涨跌额和涨跌幅生成 qfq/hfq：

- 事件日反推前收：`impliedPrevClose = close - changeAmount`；涨跌额不可用时退化为 `close / (1 + changePercent / 100)`
- 若 `impliedPrevClose` 与原始前收存在超出舍入噪声的差异，认为发生除权除息
- 事件因子：`factor = impliedPrevClose / rawPrevClose`
- qfq：以全历史最新交易日为基准，历史价格逐段累乘事件因子，再切片返回请求区间
- hfq：以可得最早交易日为基准，事件后价格逐段除以事件因子
- OHLC 按同一因子的价格倍数调整；成交量和成交额保持不变
- 因子缺失或覆盖不完整时回退为拉取全历史日线重新建链

**理由**：实测搜狐在除权除息日的涨跌额/涨跌幅已按除权口径给出，例如贵州茅台 2025-06-26 原始收盘 1420.00、搜狐涨跌额 +11.74，可反推除权后前收 1408.26。该信息足以推导因子链。

**备选方案**：用日线自有涨跌价差自行判断复权。  
**未采用原因**：除权除息日原始价差会被误判为跌幅，无法得到正确因子。

### D5：三条任务共享一次搜狐 raw 请求

**决策**：适配器内部按 `symbol + startDate + endDate` 维护有界的 in-flight 缓存。raw、qfq、hfq 三个任务在相同区间内复用同一次搜狐原始日线响应，各自根据 `adjust` 返回不同价格序列。缓存条目需设置容量上限和失败清理。

**理由**：现有同步服务仍按三类任务调度，如果不复用请求，单只股票会被请求三次。缓存能在不改变任务语义的前提下减少上游压力。

**备选方案**：把三类任务合并成一次任务同时产出三种数据。  
**未采用原因**：会改变 `DAILY_KINDS`、`last_success_date` 和失败重试语义，超出本 change 范围。

### D6：全量与增量行为

**决策**：

- 全量回填：适配器按 `19900101 ~ 最新交易日` 拉取搜狐 raw 日线；raw 任务直接使用，qfq/hfq 任务从同一份 raw 数据派生。
- 增量下载：raw 任务只请求 `nextTradingDay(last_success_date) ~ 最新交易日`。
- qfq/hfq 增量优先复用当前进程因子缓存；缓存缺失时读取 `adjust_factors` 中历史因子，并用增量区间数据识别新事件。
- 若历史因子缺失、覆盖不完整，或增量区间发生除权除息，允许适配器回退为全历史日线重建因子链；现有 `rescaleQfqHistory()` 的全历史 qfq 重标定逻辑保持不变。

**理由**：qfq 基准依赖最新交易日，hfq 基准依赖上市首日；增量不能只凭局部区间独立计算。优先复用已有因子可以保持增量效率，回退全历史保证正确性。

**备选方案**：每次 qfq/hfq 增量都拉全历史。  
**未采用原因**：全市场增量成本过高，且会让 RPS 成为瓶颈。

### D7：数据源标识与失败处理

**决策**：`DAILY_RAW_SOURCE` 改为 `sohu_hisHq`。搜狐 K 线失败时只使用现有任务重试机制，不回退东财；错误日志保留 URL、股票代码、复权类型、日期区间和底层 cause。切换后已有行情库需重新执行全量回填，增量更新在全量任务完成前仍被拒绝。

**理由**：混用东财与搜狐数据会让 `source` 和因子口径失真；明确失败和重新回填比静默回退更可诊断。

**备选方案**：搜狐失败时回退 `stock-sdk`。  
**未采用原因**：会形成双源混合口径，且掩盖搜狐接口问题。

### D8：因子读取器注入与来源标识

**决策**：`createSohuKlineClient()` 接受只读因子读取器依赖 `readFactors(stockCode): MarketFactorRow[]`，由 `getMarketSyncService()` 使用 `readAdjustFactors(db, stockCode)` 注入。搜狐适配器仅在 qfq/hfq 增量且内存因子缓存缺失时调用该读取器；读取失败或覆盖不完整时回退全历史日线重建。同时将 `FACTOR_SOURCE` 改为 `derived:sohu_hisHq`，使 `replaceAdjustFactors / upsertAdjustFactors` 写入的 `adjust_factors.source` 与本地推导口径一致。

**理由**：`marketSdkClient` 自身不持有行情库连接；重启后的增量必须复用历史因子，否则只能每次全历史回退。来源标识需要同时覆盖原始日线和因子表，避免混源。

**备选方案**：让 `marketDataSyncService` 直接读取因子并传给适配器。  
**未采用原因**：会把数据源细节扩散回同步服务，破坏 D1/D2 的边界。

### D9：采用最小间隔匀速限流

**决策**：同步服务的 HTTP 请求不再使用 1 秒滑动窗口，而按 `intervalMs = floor(1000 / rps)` 匀速放行；默认 `rps = 3`，即相邻请求至少间隔 333ms。

**理由**：真实全历史回填验证中，滑动窗口 4 req/s 允许前几个请求在几毫秒内连续发出，触发搜狐 HTTP 503。匀速限流限制相邻请求间隔，可避免短时突发，同时保持 Spring 的平均速率。

**备选方案**：继续使用滑动窗口并把默认值降到 3 req/s。  
**未采用原因**：滑动窗口仍允许短时突发，无法保证相邻请求最小间隔。

## Risks / Trade-offs

- [搜狐接口非官方，字段或参数可能变化] → 使用集中适配器封装请求与解析，所有解析异常进入现有失败重试和日志；不把第 11 字段作为事实依据。
- [qfq/hfq 为本地推导，可能与东财显示值不完全一致] → 以除权除息日因子跳变对齐为准，抽样对比东财并记录差异；用户已接受该差异。
- [成交额单位可能与现有库口径不一致] → 实现阶段用样本股对比东财成交额，确认万元→元换算后再提交落库。
- [qfq 基准需要全历史因子链] → 增量优先读取 `adjust_factors`，缺失时回退全历史重建；保留现有 qfq 重标定逻辑。
- [三条任务共享缓存导致内存占用] → 缓存设置容量上限、过期清理和失败清理；只缓存当前同步区间。
- [滑动窗口 4 req/s 的短时突发触发搜狐 503] → 改用 333ms 最小间隔匀速限流；如仍出现 503，通过 `meta.sync_rps` 下调速率。
- [已有行情库混源] → 修改数据源标识，并要求切换后重新全量回填。

## Migration Plan

1. 新增搜狐 K 线客户端与因子推导模块，补单元测试。
2. 将 `marketSdkClient.ts` 改为混合客户端，仅替换 `getHistoryKline()`。
3. 更新 `DAILY_RAW_SOURCE` 为 `sohu_hisHq`、`FACTOR_SOURCE` 为 `derived:sohu_hisHq`，并在构造 wiring 中注入只读因子读取器。
4. 使用 20～50 只股票做小样本全量回填，验证字段映射、成交额单位、因子跳变日和任务状态。
5. 执行增量补跑，验证 `last_success_date` 推进、新除权事件处理和因子刷新。
6. 提示用户对已有行情库重新执行全量回填；确认旧东财数据不再被增量更新续写。
7. 回滚策略：恢复 `marketSdkClient` 到 `stock-sdk` 实现并重新全量回填行情库；前端与业务库无需回滚。

## Open Questions

- 搜狐成交额单位需在实现阶段完成样本回归，最终换算系数以对比结果为准。
- 333ms 最小间隔的长期稳定性仍需通过真实全量回填验证；如出现 503，下调 `meta.sync_rps`。
- 超长历史区间的单次请求稳定性需通过小样本回填观察；如不稳定，按年份或固定年数切分请求区间。
