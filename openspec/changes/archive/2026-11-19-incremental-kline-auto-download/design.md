## Context

**现状链路**

- 自动下载入口：`performAutoDownload()`（`electron/services/klineDownloadService.ts:658-723`），交易日判断后以 `today ~ today` 调用 `downloadBatch`（`:675-687`）。
- 周期分层：日线完成后再调 `refreshRecentPeriodKline()`，用固定 `now-30d` / `now-90d` 覆盖重下周线与月线（`:626-651`）。
- 批量执行：`downloadBatch(stocks, startDate, endDate, adjustTypes, period, options)` 全批共用一个 `startDate`（`:537-618`），逐只串行、互斥标志 `batchDownloading`、整批末尾 `saveDatabase()` 一次。
- 落库：`saveKlineData()` 走 `ON CONFLICT(stock_code, trade_date, adjust_type) DO UPDATE`（`electron/database.ts:1069-1106`），即**已有日期是覆盖更新**；周/月线在批次含当前周期记录时先 `DELETE ... WHERE trade_date >= 当前周期起点`（`:1050-1062`）。
- 表与索引：`kline_daily` / `kline_weekly` / `kline_monthly`，索引 `idx_kline_<period>_code_date_adjust` 已存在（`sql/migrations/001_init.sql:142-150`），`MAX(trade_date)` 可按索引定位。
- 调度：`scheduleNextDownload()`（`:729-756`）用墙钟差算 `delay` 交给 `setTimeout`，回调里 `await performAutoDownload()` 后递归调度。
- 交易日历：`sdk.getTradingCalendar()`（`:331`）返回**整年**已排序日期数组（实测 1990-12-19 ~ 2026-12-31，含未来交易日、排除法定假期、无重复），应用层按「同一天」缓存、SDK 层 12h TTL。

**约束**

- 运行时数据库是 sql.js 单文件，写盘代价高（整库序列化），因此新增逻辑必须是**只读查询 + 复用既有写入批次**。
- 数据源对周/月线的未完成周期返回「最新交易日」作为 `trade_date`（既有 `未完成周期的覆盖写入` 需求），增量后这一点不变。
- 手动下载的语义（用户显式指定区间）必须完全不受影响。

## Goals / Non-Goals

**Goals:**

- 自动下载从「固定当天」变成「接着库内最新数据补到最近交易日」，失败可自然补偿。
- 周线/月线去掉硬编码的 30/90 天窗口，与日线使用同一套增量口径。
- 消除「定时器提前触发 → 当天执行两次」的结构性缺陷。
- 应用在计划时刻之后启动时，能自行判断当日缺失并补齐，无需等待下一次调度或人工手动下载。
- 不引入数据库迁移、不改变手动下载行为。

**Non-Goals:**

- 不修复库内中间缺口（人工处理）。
- 不做复权因子变化检测（除权除息后人工全量重下）。
- 不做「当日已执行」标记、不做交易日历落盘。
- 不调整 15:10 这个时刻，不引入分钟级 tick 调度。

## Decisions

### D1：起点包含库内最新日，不 +1 天

**决策**：`startDate = MAX(trade_date)` 对应的那天本身。

**理由**：

1. 15:10 拉取的当日 bar 可能未定稿，次日重取同一交易日可覆盖修正（UPSERT 幂等）。
2. 数据源偶尔会修正近端历史 bar。
3. 成本只是多 1 根 bar，而「+1 天」需要额外的交易日历运算，且一旦库内最新日与数据源交易日历不一致（停牌、数据源缺 bar）就会漏数据。

**代价**：每次多请求 1 天的数据量，可忽略。

### D2：起点取「不复权」与「前复权」中更早的那天，而非逐复权类型起点

**决策**：按 `(stock_code, adjust_type)` 分别取 `MAX(trade_date)`，再取两者的最小值作为**整只股票**的唯一起点。

**理由**：`downloadKline()` 对一批 `adjustTypes` 共用一个 `startDate`（`:242`），逐类型起点需要改动 `downloadKline` / `downloadWithRetry` / `downloadBatch` 三层签名，且结果聚合（`KlineDownloadResult` 的 unadjustedCount / adjustedCount）会变得更绕。取更早者可自动补齐落后的一方（例如某次 qfq 失败），重复下载由 UPSERT 吸收。

**代价**：两种复权同步良好时，会多下若干根「另一种复权已有」的数据。以自选股规模（数十只）计可忽略。

**替代方案**：逐复权起点 → 请求更省，但签名与聚合复杂度显著上升，且当前收益不明显，不采用。

### D3：有数据时不设回看下限；无数据时回退到 19900101

**决策**：

- 库内有数据：起点严格等于库内最新日，不做「至少回看 30 天」之类的兜底。
- 库内无数据（该股在该周期表中完全没有记录）：起点回退为常量 `EARLIEST_START_DATE = '19900101'`，即拉取数据源可得的全部历史，而非只拉终点当天。

**理由**：

1. 用户明确「中间缺口交给人工处理」，有数据时加回看下限会让每只股票每次都重复拉取整段窗口，与增量的初衷相悖。
2. 无数据是「从未下载过」的状态（新股入自选、清库、新增周期表），此时不存在增量起点，只能有两种选择：只拉当天（历史永久空缺，依赖人工补）或拉全量。用户选择全量，避免用户为每只新股票手动发起一次历史下载。
3. `19900101` 早于 A 股首个交易日（交易日历实测起始 `1990-12-19`），可安全作为「从头」的语义标记；不取 `19901219` 是为了不把日历边界写死进业务逻辑。

**代价**：

- 首次自动下载时，无数据股票的单次请求区间可能长达 30 年以上，请求耗时与返回体量显著高于增量场景；仅在「从未下载」时发生一次。
- 数据源对超长区间的返回行为需在验证阶段实测（见 Risks）。

**注意**：`19900101` 只是起点，实际返回条数由数据源按上市日期截断；不得据此认为每只股票都会得到 1990 年起的数据。

### D4：终点取「<= 今天」的最近交易日，回退规则显式化

**决策**：新增 `getLastTradingDay()`，从 `getTradingCalendar()` 的有序数组里取最后一个 `<= today` 的日期（转 `YYYYMMDD`）；异常回退：

- 日历为空 / 接口失败 → 回退「排除周末」规则（与 `isTradingDay()` 现有回退一致），并 `log.warn`。
- 日历最后一条 `< today`（年度文件未更新）→ 同样回退「排除周末」，并 `log.warn`，**不得**把过期日期当作终点。

**理由**：日历含全年未来交易日，天然排除法定假期；`getTradingCalendar()` 已有两层缓存，调用成本可忽略。过期兜底避免跨年后把一个陈旧日期当作终点、从而漏拉新一年的数据。

**替代方案**：直接用 `today` 作为终点、让数据源返回实际最后一根 bar → 非交易日会稳定产生空结果与失败日志，且无法区分「数据源延迟」与「无数据」，不采用。

### D5：`downloadBatch` 的股票项增加可选 `startDate`，手动路径不变

**决策**：

```ts
export interface DownloadStockInput {
  stockCode: string;
  stockName: string;
  /** 该股本次的下载起始日（YYYYMMDD）；缺省则用整批 startDate */
  startDate?: string;
}
```

`downloadBatch` 内逐只取 `const from = stock.startDate ?? startDate`，并按 `from` 校验；**单只起点非法时回退整批 `startDate` 并 warn，不整批失败**（起点来自只读查询，属于内部数据，异常不应波及用户手动发起的批次）。

**理由**：调用方（自动下载）已经知道每只股票的起点，把它塞进入参比让 `downloadBatch` 自己查库更清晰，也让 `downloadBatch` 保持「纯执行器」定位；手动批量下载走 IPC 时不传该字段，行为完全不变。

**约束**：`startDate` 必须钳制到 `<= endDate`（防库内脏的未来日期导致 `validateDateRange` 抛错、整批被拒）。

### D6：周线/月线复用同一增量规则，删除固定窗口

**决策**：`refreshRecentPeriodKline()` 不再计算 30/90 天，而是与日线一样按各自表内的 `MAX(trade_date)` 取起点，终点同样为最近交易日。

**理由**：未完成周期的 `trade_date` 是「最新交易日」，所以 `MAX` 本身就落在当前周期内；`saveKlineData` 的「含当前周期则先删后插」逻辑保证同一周/月只留一行。固定窗口的唯二作用（覆盖当前周期、补近期失败）被增量规则完全覆盖。

**注意**：若某股周线数据落后多周，新的起点会把缺失的周线一次性补齐，属于期望行为。

### D7：调度加最小间隔保护，不做当日幂等标记

**决策**：

```ts
const MIN_LEAD_MS = 2 * 60 * 1000;
// 距目标时刻不足 2 分钟视为「已过」，排到下一个调度日
if (now.getTime() + MIN_LEAD_MS >= target.getTime()) {
  target.setDate(target.getDate() + 1);
}
```

**理由**：本次故障的根因是「提前触发后，递归调度又把当天 15:10 排了一次」，用最小间隔即可从结构上消除，且不引入任何跨天状态。用户明确评估过「当日已执行」内存标记（`lastAutoDownloadDay`）后选择不做，因此不实现。

**代价**：调度精度被限制在「至少提前 2 分钟安排」，即 15:08 之后启动应用不会在当天执行。这与现状（15:10 后启动即排明天）语义一致，只是把边界从 15:10 提前到 15:08。

**待观察**：提前触发的具体原因（NTP 校正 / 休眠唤醒）无法在代码层面完全排除，若再次出现提前超过 2 分钟的情况，需要再评估是否改为「每分钟 tick + 日期判断」。

### D8：日期口径统一走本地时区

**决策**：新增 `localDateYmd()`（与 `getCurrentPeriodStart` 的拼串方式一致），自动下载的「今天」、终点计算、起点格式化全部使用它；不再使用 `new Date().toISOString()`（UTC）。

**理由**：凌晨 0–8 点 `toISOString()` 会给出前一天，终点会算错。现有 `performAutoDownload`（`:676`）与 `validateDateRange`（`:140`）都有这个隐患，本次一并收口。

**范围**：只在自动下载链路内替换，`validateDateRange` 的 UTC 取值保持不动（避免扩大改动面与影响手动下载行为）。

### D9：启动补跑用「数据完整度」判定，不做执行标记

**决策**：

- 触发条件：本地时间 `>= 当日 15:10`（即 `isPastDailyScheduleTime`）。早于该时刻启动的实例不补跑，交给当天的定时任务。
- 完成判据：`isPeriodComplete(latest, endDate)` —— 该股该周期「不复权」与「前复权」的最新交易日**都** `>= endDate` 才算完成；任一缺失或落后都算未完成。
- 只对未完成的股票发起下载（`collectPendingStocks` 逐只分组），已完成的股票不发请求，仅在日志里记录跳过数与待补区间。
- 三个周期全部完成时不做任何请求，只记一行「当日 K 线已完整」。
- 定时任务与启动补跑共用同一个 `performAutoDownload()`，因此两条入口的判定完全一致。

**理由**：

1. 增量起点本来就从 `MAX(trade_date)` 推导，完成判据与起点计算是同一份数据、同一个语义，不需要新增状态。
2. 用户明确否决过「当日已执行」内存标记；用数据判定天然跨重启有效，且不会出现「标记说跑过了、但数据其实没落盘」的不一致。
3. 「只补未完成」让补跑成本与缺失量成正比；如果整批重跑，已完成股票也要各发 2 次请求（两种复权）。

**代价**：

- 停牌股/退市股的最新交易日永远早于终点，因此每次 15:10 之后启动都会把它判为未完成并重试一次（日线增量区间只有 1 天，成本低）。用户已确认接受，不做额外标记抑制。
- 15:08–15:10 之间启动的实例既不触发补跑（未到 15:10），定时器也已因 `MIN_LEAD_MS` 顺延到次日，当天不会下载；这是 2 分钟的边界窗口，与现状一致。
- 启动后会立即发起网络请求，首屏可能短暂繁忙；因此调用点用 `void` 不阻塞窗口显示。

**替代方案**：落盘「当日已执行」标记 → 能抑制停牌股重试，但需新增持久化状态并处理「标记与实际数据不一致」，用户选择不用。

## Risks / Trade-offs

| 风险 | 影响 | 处置 |
|---|---|---|
| 除权除息后前复权历史基准不一致 | 新旧 qfq 数据拼接处跳空，影响图表与形态检测 | 用户已确认人工全量重下；在 spec 中写成明确约束 |
| 中间缺口不自愈 | 库里长期存在空洞 | 用户已确认人工处理；spec 写明 |
| 库内最新日远早于今天（长期未运行） | 一次下载的区间变长（可能数年） | 数据源单请求可承受，且属首次/恢复场景，接受 |
| 库内最新日 == 终点 | 区间只含 1 天，当日未定稿时数据可能不准 | 次日增量会自动覆盖同一交易日 |
| 周/月线起点落在区间中部的边界行为 | 数据源可能返回区间外起点的 bar | 落库时若有当前周期记录会先删后插；需在验证阶段实测一次周/月线区间下载结果 |
| 无数据股票返回 0 条 | 记为失败（`count > 0` 判定） | 保持现状；增量后停牌股票会从自己的最新日重新拉取，通常仍返回 ≥1 条，噪声较现状更低 |
| `MIN_LEAD_MS` 使 15:08–15:10 之间启动的应用当天不执行 | 极端情况下当天缺失 | 次日增量自动补齐；与现状边界一致 |
| 无数据股票单次请求跨度 30 年以上 | 请求耗时与返回体量骤增，可能触发数据源超时或静默截断 | 仅在「从未下载」时发生一次；验证阶段实测一只无数据股票的全量结果，若被截断则需改为按年分段请求 |
| `19900101` 起点对周线/月线同样生效 | 首次自动下载即拉取全量周线/月线 | 属期望行为；`saveKlineData` 的当前周期先删后插逻辑不受影响 |
| 本地新增自选股后自动补齐全量历史 | 单次自动下载任务时长上升（数十只新股票时更明显） | 串行逐只执行、互斥标志与整批落盘不变；耗时可接受，如不可接受再评估分批 |
| 停牌股每次启动补跑都被判为未完成 | 每天多一次请求与失败日志 | 用户已确认接受；日线增量区间只有 1 天 |
| 启动补跑与手动下载并发 | 批量互斥标志拒绝其中一方 | 自动侧记录「已有批量任务」后退出，不排队重试 |
| 上次下载数据在内存中但落盘失败 | 重启后判为未完成并重新下载 | 期望行为，属自愈；落盘失败本身是另一个待修问题 |

## Migration

无数据库结构变更，无数据迁移。仅新增只读查询与调度逻辑，旧库直接可用。
